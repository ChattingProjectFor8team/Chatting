# 황도윤 Member + ArtistContent 설계 이유 정리 

이 문서는 `README`로 옮기기 전, `member + artistcontent` 파트에서 실제로 어떤 설계 선택을 했고 왜 그렇게 했는지 정리한 검토용 초안이다.
`README`나 포트폴리오 본문에 바로 넣을 짧은 버전은 [`member-artistcontent-readme-summary.md`](member-artistcontent-readme-summary.md)에 따로 정리한다.

정리 기준은 아래 두 가지다.

- `HANDOFF_revised.md`에 남아 있는 구현 흐름과 의사결정 기록
- `member`, `artistcontent`, `global/common/config` 하위 코드 주석과 현재 구현

주의할 점도 있다.

- 아래 내용 중 상당수는 코드 주석과 핸드오프에 직접 명시된 내용이다.
- 일부는 코드 형태와 주석을 함께 보고 정리한 `해석`이다.
- 그래서 README로 옮길 때는 "코드에서 확인되는 사실"과 "설계 의도 해석"을 구분해 다듬는 편이 좋다.

## 1. 아티스트 검색은 `v1 원본 조회`, `v2 로컬 캐시`, `v3 Redis 캐시`를 분리했다

`GET /api/member/v1/artists/search`는 원본 조회 API로 남기고, `GET /api/member/v2/artists/search`에는 과제용 로컬 캐시를, `GET /api/member/v3/artists/search`에는 실사용 기본인 Redis remote cache를 붙였다.

- 선택
- `v1`은 캐시 없는 기준선 API로 유지했다.
- `v2`는 `Caffeine` 로컬 캐시를 사용했다.
- `v3`는 `Redis` remote cache를 사용했다.
- 검색 결과는 `페이지당 10건`으로 고정했다.
- 사용자는 `page`를 넘겨 다음 페이지를 볼 수 있지만, `size`는 바꿀 수 없게 했다.
- 캐시 키는 `keyword.trim().toLowerCase(Locale.ROOT) + page` 기준으로 정규화했다.

- 이유
- 과제 요구사항상 "캐시 없는 원본 API"와 "캐시 적용 API"를 둘 다 보여줄 필요가 있었다.
- 검색은 같은 키워드가 반복되는 경향이 강해서 읽기 최적화 효과를 설명하기 좋다.
- 사용자가 `size`를 임의로 크게 늘리면 한 번의 요청이 과도하게 무거워질 수 있다.
- 그래서 "다음 페이지는 볼 수 있지만, 한 번에 보는 크기만 10건으로 고정"하는 쪽을 택했다.
- `size`를 고정해 두면 캐시 키가 `keyword + page` 정도로 단순해지고, 사용자가 `size=10000` 같은 형태로 요청을 비대하게 만드는 것도 막을 수 있다.
- 다만 `v2` 로컬 캐시 선택은 어디까지나 과제 요구사항을 맞추기 위한 성격이 강하다.
- 대용량 트래픽과 여러 서버 운영을 전제로 보면, 로컬 캐시만으로 검색 캐시를 설명하는 것은 한계가 크다.
- 서버가 여러 대면 각 서버 메모리에 캐시가 따로 생기고, 같은 검색이라도 어느 서버를 탔는지에 따라 캐시 hit와 데이터 일관성이 갈라질 수 있기 때문이다.
- 그래서 실서비스 관점에서는 Redis 같은 remote cache가 더 자연스러운 선택에 가깝고, 현재 기본 사용 버전도 `v3`로 보는 것이 맞다.

- 얻는 이득
- `v1 vs v2 vs v3` 성능 비교가 명확해진다.
- 같은 검색어 재요청은 DB를 다시 때리지 않고 로컬 메모리에서 바로 응답할 수 있다.
- 여러 서버 운영을 전제로 해도 `v3`는 캐시를 공유할 수 있다.
- 페이지당 10건으로 제한해 캐시 엔트리 크기와 메모리 사용량을 통제할 수 있다.
- 공백/대소문자 차이로 캐시가 쪼개지는 문제를 줄인다.
- 사용자가 임의로 size를 크게 키워 한 번의 조회 비용을 폭증시키는 것을 막을 수 있다.

- trade-off
- 페이지가 바뀌면 캐시 키도 달라지므로, 첫 페이지 하나만 캐시하던 구조보다 캐시 엔트리는 조금 더 늘어난다.
- 로컬 캐시는 scale-out 시 서버 간 공유가 안 된다.
- Redis remote cache는 네트워크 왕복이 추가되므로 warm hit 절대속도는 로컬 캐시보다 느릴 수 있다.
- 검색 조건이 단순 `LIKE` 기반이라 전문 검색의 정확도나 확장성은 제한적이다.

핸드오프 기준 해석으로는, 이 검색 설계는 "실서비스 최적안"이라기보다
"과제 요구사항을 만족시키면서 검색 캐시 비교 축을 만들되, 실제 사용 기본값은 Redis remote cache로 가져가려는 선택"으로 읽는 것이 더 맞다.

## 2. 검색 캐시는 `즉시 전량 무효화` 대신 `짧은 stale 허용 + TTL 자연 만료`를 택했다

- 선택
- 아티스트 create/update/delete 시 `artist detail cache`는 비우지만, `artist search v2/v3` 전체 엔트리를 강제로 전량 eviction 하지는 않았다.
- `artistSearchV2` 로컬 캐시는 `TTL 10분`, `maximumSize 1000`으로 제한했다.
- `artistSearchV3` Redis 캐시도 `TTL 10분`을 둔다.

- 전제
- 로컬 캐시 적용 자체는 과제 요구사항에서 출발했다.
- 실제 서비스, 특히 대용량 트래픽과 scale-out을 전제로 보면 검색 캐시는 Redis 같은 remote cache 쪽이 더 자연스럽다.

- 이유
- 검색 캐시는 키워드 조합이 매우 많다.
- 아티스트 한 건이 바뀌었다고 해서 어떤 키워드 조합 캐시가 영향을 받는지 역추적하는 비용이 크다.
- 검색 결과는 상세 정보보다 약한 일관성을 허용해도 사용자 경험이 크게 깨지지 않는다고 판단했다.

- 얻는 이득
- 검색 키워드 조합마다 역인덱스를 따로 관리하지 않아도 된다.
- 캐시 무효화 로직이 단순해진다.
- 반복 조회가 많은 키워드는 TTL 동안 높은 hit rate를 유지할 수 있다.

- trade-off
- 아티스트 정보 수정 직후 잠깐 동안은 검색 결과가 stale할 수 있다.
- "수정 즉시 검색 결과도 반드시 최신이어야 한다"는 요구가 강해지면 현재 전략은 한계가 있다.

이 설계는 "강한 실시간 일관성"보다 "캐시 적중률과 운영 단순성"을 우선한 결정이다.

## 3. 인기 검색어는 검색 결과 캐시와 분리해서 `Redis ZSet + 사용자 중복 제거`로 집계했다

- 선택
- 인기 검색어 집계는 검색 결과 캐시와 별개로 `Redis ZSet`에 두었다.
- 동일 사용자의 동일 검색어는 `24시간` 동안 한 번만 점수를 올린다.
- 키워드와 사용자 식별자 모두 `trim + lowercase` 정규화를 거친다.
- 인기 검색어 조회는 `offset` 기반으로 다음 묶음을 볼 수 있게 두되, `한 번에 보는 크기`는 `10개`로 고정했다.

- 이유
- 검색 결과 캐시와 인기 검색어 집계는 목적이 다르다.
- 검색 결과 캐시는 "응답 속도" 문제이고, 인기 검색어는 "랭킹 집계" 문제다.
- 같은 사용자가 같은 키워드를 연타하면 실제 인기보다 랭킹이 왜곡될 수 있다.
- Redis ZSet은 점수 증가와 상위 N개 조회가 단순하다.
- 인기검색어도 사용자가 `size`를 임의로 크게 늘리는 대신, `10개씩 다음 묶음으로` 넘겨 보는 구조가 더 안전하다고 봤다.

- 얻는 이득
- 인기 검색어 API가 DB 없이 빠르게 동작한다.
- 동일 키워드의 공백/대소문자 파편화를 막는다.
- 동일 사용자 반복 입력을 걸러 랭킹 왜곡을 줄인다.
- 사용자가 한 번에 큰 묶음을 요청해 Redis 조회량을 과도하게 키우는 것을 막을 수 있다.

- trade-off
- dedupe 기준이 현재는 `principal/email` 수준이라, 더 정교한 디바이스/세션 정책은 아니다.
- 집계 기간을 24시간 TTL로 둔 만큼 "실시간 급상승"과 "장기 누적 인기"를 동시에 설명하지는 못한다.
- 페이지당 크기는 고정이라, 클라이언트가 더 큰 한 번 조회를 원해도 허용하지 않는다.

## 4. 아티스트 상세는 검색과 다르게 `Redis Cache-aside`를 적용했다

- 선택
- `getArtistV2`는 Redis 캐시를 사용한다.
- `updateArtist`, `deleteArtist`, `ArtistMember` 변경 경로에서는 상세 캐시를 명시적으로 비운다.

- 이유
- 상세 조회는 `artist + artistMember 목록`을 함께 조립한다.
- 검색보다 조회 키가 단순하고, 어떤 캐시를 비워야 하는지도 명확하다.
- 아티스트 상세는 홈, 상세 페이지, 멤버 정보 표시 등에서 반복 사용되기 좋다.

- 얻는 이득
- 조회 키가 `artistId` 하나라서 캐시 설계가 단순하다.
- 수정/삭제 시 어떤 캐시를 비워야 하는지가 분명하다.
- 상세 응답 조립 비용과 반복 DB hit를 줄일 수 있다.

- trade-off
- 상세는 검색보다 일관성 요구가 높아 update/delete 시 eviction 책임이 더 많다.
- 캐시 TTL을 너무 길게 두면 프로필/커버 이미지 변경 반영이 늦어진다.

## 5. `slug`와 이미지 업로드 흐름은 "운영 식별자"와 "저장 경로 안정성"을 기준으로 잡았다

- 선택
- `slug`는 `^[a-z0-9-]+$`만 허용한다.
- 아티스트 생성 시 엔티티를 먼저 저장하고, 그 뒤 대표 이미지 업로드를 처리한다.
- 이미지 교체는 `새 파일 업로드 -> 기존 URL best-effort 삭제` 순서를 사용한다.

- 이유
- `slug`는 표시용 이름이 아니라 URL 식별자라서 자유도를 너무 크게 주지 않았다.
- 이미지 저장 경로는 `artistId`가 있어야 안정적으로 만들 수 있다.
- 수정 시 기존 파일을 먼저 지우면 새 업로드 실패 시 복구가 어렵다.

- 얻는 이득
- URL 식별자 품질과 일관성을 유지할 수 있다.
- 파일 경로 정책을 단순하게 유지할 수 있다.
- 이미지 교체 실패 시 기존 데이터 손상 가능성을 줄인다.

- trade-off
- 사용자 친화적인 한글/특수문자 slug는 허용하지 않는다.
- best-effort delete 구조라, 예외 상황에서는 사용자와 DB 기준으로는 이미 새 이미지로 정상 반영됐더라도, S3에만 이전 파일이 남는 orphan 정리 과제가 남을 수 있다.

## 6. 피드 목록은 전반적으로 `offset`보다 `cursor slice`를 우선했다

- 선택
- `FanPost`, `ArtistPost`, 댓글 root 목록, YouTube 목록은 모두 `id DESC` 기반 cursor slice를 쓴다.
- 한 번에 내려주는 기본 크기는 대체로 `10` 또는 `20`으로 고정했다.

- 이유
- 피드는 새 글이 계속 위로 쌓이는 구조다.
- `offset` 페이지네이션을 쓰면 1페이지와 2페이지 사이에 새 글이 들어왔을 때 중복/누락이 생기기 쉽다.
- cursor는 "마지막으로 본 id보다 오래된 것만" 가져오므로, 무한 스크롤과 최신순 정렬에 더 잘 맞는다.

- 얻는 이득
- 새 글 삽입이 일어나도 다음 페이지 중복 가능성을 줄일 수 있다.
- `artist_id + id DESC` 같은 복합 인덱스와 결합하기 쉽다.
- 무한 스크롤 UX와 잘 맞는다.

- trade-off
- 임의 페이지 점프에는 불리하다.
- 총 페이지 수를 쉽게 보여주기 어렵다.
- 프론트가 `cursor`를 상태로 들고 있어야 한다.

## 7. HOT 목록은 도메인별로 다른 페이지네이션을 일부러 남겼다

### 7-1. FanPost HOT은 `score + id 복합커서`를 사용했다

- 선택
- HOT FanPost는 `(likeCount + commentCount)`를 점수로 보고, 정렬은 `score DESC, id DESC`를 사용한다.
- 페이지네이션도 `scoreCursor + idCursor` 복합커서를 사용한다.

- 이유
- HOT 정렬 기준이 단순 id가 아니라 score이기 때문이다.
- score는 좋아요/댓글 증가에 따라 계속 바뀌므로, offset으로는 페이지 경계가 쉽게 흔들린다.
- 정렬 기준과 페이지 기준을 같은 축으로 맞추는 편이 안정적이다.

- 얻는 이득
- HOT 목록에서도 "정렬 기준"과 "다음 페이지 기준"이 일치한다.
- 반응 수가 계속 변하는 목록에서 offset보다 중복/건너뛰기 위험을 줄일 수 있다.
- 과제 발표 때 "왜 일반 피드와 HOT 피드의 커서 설계가 달라졌는지"를 설명하기 좋다.

- trade-off
- 일반 cursor보다 구현 복잡도가 높다.
- score 변동이 심한 동안에는 완전한 스냅샷 일관성까지 보장하는 것은 아니다.

### 7-2. FanLetter HOT은 `offset slice`를 남겨 비교 학습 포인트로 사용했다

- 선택
- HOT FanLetter는 `offset + size`를 사용한다.
- 후보군은 `최근 24시간 + 좋아요 5개 이상`으로 좁힌다.

- 이유
- FanLetter는 댓글이 없어서 score 축이 단순하다.
- HOT 후보군이 FanPost보다 작다고 보고, 구현을 단순하게 가져갔다.
- 핸드오프와 코드 주석 기준으로, FanPost와 일부러 다른 방식을 남겨 비교 학습 포인트로 삼은 의도도 있다.

- 얻는 이득
- 구현과 설명이 단순하다.
- FanPost HOT과 대비해 "왜 어떤 목록에는 복합커서가 필요하고, 어떤 목록은 offset으로도 충분한지"를 발표할 수 있다.

- trade-off
- 후보군이 커지거나 반응 변화가 심해지면 offset 안정성이 떨어질 수 있다.
- HOT 정책이 더 커지면 이후 cursor 기반으로 다시 옮겨야 할 수 있다.

## 8. HOT 기준은 "그냥 상위 N"이 아니라 `반응 없는 글 제외` 정책으로 정리했다

- 선택
- FanPost HOT은 `최근 24시간 + 좋아요 5개 이상 또는 댓글 5개 이상`을 후보로 본다.
- FanLetter HOT은 `최근 24시간 + 좋아요 5개 이상`을 후보로 본다.

- 이유
- 단순 최신순 상위 N은 HOT이라는 이름과 맞지 않는다.
- 반응이 거의 없는 글이 HOT에 섞이면 사용자 기대와 어긋난다.
- FanPost와 FanLetter는 상호작용 구조가 달라 기준을 완전히 같게 두지 않았다.

- 얻는 이득
- HOT 탭 의미가 더 명확해진다.
- 최근성만 높은 글과 실제 반응이 있는 글을 구분할 수 있다.

- trade-off
- 임계값은 도메인 지식이 섞인 하드코딩 정책이라 운영 중 다시 조정될 가능성이 높다.
- HOT 전용 캐시를 따로 붙일지 여부는 아직 후속 검토 포인트로 남아 있다.

## 9. `base cache + hot cache` 분리는 "변하지 않는 것"과 "자주 바뀌는 것"의 수명을 분리하기 위한 선택이었다

- 선택
- `FanPost`, `ArtistPost`, `FanLetter`는 모두 `base cache + hot cache` 구조를 쓴다.
- `base cache`에는 본문, 작성자, 미디어, 해시태그, 수신자, 배지 등 상대적으로 안정적인 조립 결과를 넣는다.
- `hot cache`에는 `likeCount`, `commentCount`처럼 자주 변하는 숫자만 둔다.

- 이유
- count까지 base에 섞어 캐시하면 전체 TTL을 짧게 잡아야 한다.
- 그러면 미디어/해시태그 같은 비싼 조립 데이터도 같이 자주 날아간다.
- 읽기 응답은 마지막 단계에서만 `base + hot`을 합치면 된다.

- 얻는 이득
- 자주 안 바뀌는 구조 데이터를 더 길게 재사용할 수 있다.
- 좋아요/댓글 수만 짧은 TTL로 따라가게 할 수 있다.
- 같은 post의 detail/list가 같은 hot data 키를 공유해 count 캐시 중복을 줄일 수 있다.

- trade-off
- 읽기 조립 단계가 한 번 더 생긴다.
- 캐시 구조가 단순 통캐시보다 복잡하다.
- base와 hot의 갱신 타이밍이 다르기 때문에 아주 짧은 stale은 감수한다.

## 10. ArtistPost에서 `base/hot` 분리를 더 강하게 드러낸 이유는 `3초 flush` 구조와 맞물리기 때문이다

- 선택
- ArtistPost는 특히 count를 base 응답에서 분리하고, `POST_HOT_DATA`를 `3초 TTL`로 뒀다.
- like/comment count flush 배치도 기본 `3초` 주기로 맞췄다.

- 이유
- ArtistPost는 현재 프로젝트에서 동시성/트래픽 설계가 가장 무거운 영역이다.
- 요청 경로에서 count를 바로 DB에 밀어넣는 대신, Redis Stream과 delta flush를 통해 늦게 반영한다.
- 읽기 캐시 TTL과 flush 주기를 비슷하게 맞추면 사용자가 체감하는 eventual consistency 리듬을 설명하기 쉽다.

- 얻는 이득
- 요청 경로에서 DB row hotspot을 줄일 수 있다.
- 화면에서 count가 완전히 제멋대로 튀는 느낌보다, 짧은 주기 리듬으로 따라오는 형태를 만들 수 있다.
- `본문은 길게 캐시`, `count는 flush 리듬에 맞춰 짧게 캐시`라는 설명이 가능해진다.

- trade-off
- count는 강한 실시간 일치가 아니라 짧은 지연을 허용한다.
- flush 실패, consumer 지연, reconcile 필요성 같은 운영 복잡도가 늘어난다.

## 11. 댓글은 post처럼 `base/hot` 분리하지 않고 `짧은 whole-response cache`를 택했다

- 선택
- 댓글 root slice와 reply list는 각각 별도 짧은 TTL 캐시를 둔다.
- root 댓글 캐시는 보수적으로 admission 한다.
- reply 캐시는 더 공격적으로 admission 한다.

- 이유
- 댓글은 post와 달리 구조 전체가 함께 움직인다.
- 댓글을 `base/hot`처럼 잘게 나누기 시작하면, 페이지 cursor나 부모 댓글 id마다 캐시 키가 많이 갈라진다.
- 그러면 댓글이 하나 추가되거나 삭제될 때 "어느 조각 캐시를 수정하거나 지워야 하는지"가 복잡해진다.
- 그래서 댓글은 잘게 쪼개 갱신하기보다, 댓글 목록 응답 자체를 짧게 통으로 캐시하고 변경 시 관련 범위를 통으로 비우는 쪽이 더 단순하다고 봤다.
- 다만 모든 댓글 응답을 무조건 캐시하면 오히려 비용이 커질 수 있어서, `heat + count threshold`를 보고 캐시에 올릴지 말지를 결정했다.

- 얻는 이득
- 정말 뜨거운 댓글 스레드에만 캐시를 쓰게 된다.
- 댓글이 적은 글은 캐시 오버헤드 없이 원본 조회로 처리한다.
- root와 reply의 성격 차이를 분리해서 대응할 수 있다.

- trade-off
- admission 정책이 단순 TTL 캐시보다 복잡하다.
- threshold 값은 운영 중 튜닝 대상이 될 수 있다.

## 12. root 댓글과 reply의 캐시 조건을 다르게 둔 이유는 조회 패턴이 다르기 때문이다

- 선택
- root 댓글 캐시는 "해당 게시글의 전체 댓글 수가 20개 이상이면서, 10초 동안 5번 이상 반복 조회될 때"만 캐시에 올린다.
- reply 캐시는 "해당 부모 댓글의 대댓글 수가 20개 이상이거나, 10초 동안 5번 이상 반복 조회될 때" 캐시에 올린다.
- 댓글 캐시는 페이지 cursor나 부모 댓글 id에 따라 여러 키로 갈라질 수 있어서, "이 게시글/이 스레드에 속한 캐시 키 목록"을 Redis에 따로 기록해 두고 변경 시 한 번에 비운다.

- 이유
- root 댓글은 전체 글 단위의 진짜 고트래픽일 때만 캐시하는 편이 낫다.
- reply는 특정 스레드 하나만 갑자기 뜨거워질 수 있다.
- 댓글은 통캐시로 읽더라도 실제 캐시 키는 cursor나 parentCommentId에 따라 나뉜다.
- 그래서 댓글이 추가되거나 삭제될 때 관련 캐시를 정확히 지우려면, "이 글/이 스레드에 대해 지금까지 만들어진 캐시 키 목록"을 따로 추적할 필요가 있었다.

- 얻는 이득
- root는 보수적, reply는 공격적으로 캐시해 실제 조회 패턴과 더 가깝게 맞출 수 있다.
- 댓글 캐시를 잘게 수정하려 들지 않고, 관련 범위만 통으로 비우는 단순한 invalidation 전략을 가져갈 수 있다.

- trade-off
- Redis에 admission heat와 scope index라는 보조 데이터가 추가로 생긴다.
- 설계 설명을 하지 않으면 왜 이렇게 복잡한지 이해하기 어렵다.

## 13. 댓글 depth는 2로 제한하고, 멘션을 `3-depth 대체 규칙`으로 사용했다

- 선택
- 원댓글은 depth 1, 대댓글은 depth 2까지만 허용한다.
- 멘션은 대댓글에서만 해석한다.
- 허용 멘션 대상은 같은 root thread 참여자로 제한한다.
- 대댓글 멘션은 최대 1명만 인정한다.

- 이유
- 댓글 구조를 무한 depth로 열면 조회, 정렬, 캐시, UI가 모두 복잡해진다.
- 대댓글까지만 허용하고 그 이후 대화 맥락은 멘션으로 대체하면 구조가 단순해진다.
- 스레드 밖 닉네임 멘션까지 허용하면 대화 범위가 흐려지고 악용 가능성도 커진다.

- 얻는 이득
- 댓글 조회 구조와 응답 shape가 단순해진다.
- 프론트 스레드 UI도 2단 구조로 고정하기 쉽다.
- 같은 스레드 안에서의 대화 맥락은 멘션으로 어느 정도 유지할 수 있다.

- trade-off
- 자유도 높은 토론형 댓글에는 한계가 있다.
- 멘션을 일반 텍스트가 아니라 부분적으로 규칙 해석하기 때문에 정책 설명이 필요하다.

## 14. 댓글 root와 reply의 정렬 방향을 다르게 둔 것도 의도적인 선택이다

- 선택
- root 댓글은 `id DESC`로 최신순 무한 스크롤을 쓴다.
- reply는 같은 스레드 안에서 `id ASC`로 오래된 순으로 읽는다.

- 이유
- root 댓글은 게시글 단위에서 "새 댓글부터 보는 경험"이 중요하다.
- 반면 reply 스레드는 대화 문맥이 중요해서 위에서 아래로 읽히는 편이 자연스럽다.

- 얻는 이득
- root는 최신 반응을 빨리 볼 수 있고, reply는 대화 흐름을 보존한다.

- trade-off
- root와 reply 정렬 규칙이 달라 구현자가 헷갈릴 수 있다.
- 응답 계약을 프론트와 명확히 맞춰야 한다.

## 15. 댓글 reply limit를 `20`으로 둔 이유는 "온디맨드 조회"와 "스레드 폭주 방어" 사이의 절충에 가깝다

- 선택
- `COMMENT_SLICE_SIZE = 20`
- `COMMENT_REPLY_LIMIT = 20`

- 이유
- root와 reply 모두 결국은 여러 묶음으로 내려갈 수 있지만, reply는 "특정 thread를 펼칠 때 먼저 작은 묶음으로 보여주는" 성격이 더 강하다.
- reply까지 너무 크게 열면 한 스레드 확장만으로도 응답 비용이 커진다.
- 너무 작게 잡으면 thread를 보는 경험이 끊긴다.

- 얻는 이득
- 한 번의 reply 확장 요청 비용을 제한할 수 있다.
- root와 reply 모두 `20`으로 맞춰 설명이 단순하다.

- trade-off
- 대댓글은 한 번에 너무 많이 읽지 않도록 20개 단위 커서 슬라이스로 제한했다.
- 한 스레드가 아주 길어지더라도 더보기 방식으로 계속 내려갈 수 있지만, 한 번의 요청으로 전부 펼쳐 읽는 구조는 의도적으로 막아 두었다.

### 15-1. 댓글 삭제는 `즉시 완전 제거`보다 `placeholder 유지 -> 마지막 child 정리` 규칙을 택했다

- 선택
- root 댓글은 자식이 없으면 바로 soft delete 한다.
- root 댓글에 자식이 남아 있으면 본문을 `삭제된 댓글입니다.` placeholder로 바꾸고 스레드에 남긴다.
- reply가 삭제될 때 placeholder 부모에 달린 마지막 자식도 함께 사라지면, 그때 부모를 실제 soft delete로 마무리한다.

- 이유
- 댓글은 단순 개별 row가 아니라 스레드 문맥을 가진다.
- 부모 댓글을 바로 감춰 버리면 아래 reply들이 남아 있어도 대화 흐름이 끊겨 보인다.
- 반대로 placeholder를 영구 보존만 하면 삭제 찌꺼기가 계속 남으므로, 마지막 child가 사라지는 시점에는 실제 정리를 해주는 편이 낫다.

- 얻는 이득
- reply가 남아 있는 동안에는 스레드 문맥을 유지할 수 있다.
- 마지막 reply까지 사라지면 placeholder도 정리돼 목록이 불필요하게 지저분해지지 않는다.
- FanPost 동기 댓글과 ArtistPost 비동기 댓글이 같은 삭제 규칙을 공유할 수 있다.

- trade-off
- 단순 soft delete보다 분기와 후처리가 복잡하다.
- 삭제 시 "자식 존재 여부"와 "placeholder 부모 최종 정리"를 같이 고려해야 해서 락 범위 설명이 필요하다.

### 15-2. 댓글 충돌 제어는 `post 전체 락`이 아니라 `root thread 락`으로만 걸었다

- 선택
- reply 생성/삭제처럼 실제 충돌 가능성이 있는 구간만 `rootCommentId` 기준 락으로 직렬화했다.
- root 댓글 생성은 스레드 경합이 없다고 보고 별도 thread lock 없이 처리한다.
- ArtistPost 비동기 댓글 consumer도 같은 thread lock 규칙을 사용한다.

- 이유
- 댓글에서 정말 순서가 중요한 것은 "같은 스레드 안의 reply 생성/삭제/placeholder 정리"다.
- 서로 다른 루트 댓글 스레드까지 같이 막아 버리면 인기 글에서 병렬성이 너무 크게 죽는다.
- 즉 필요한 정합성은 thread 단위로 지키고, unrelated thread는 흘려보내는 편이 더 낫다고 봤다.

- 얻는 이득
- 같은 글에서도 서로 다른 root thread는 병렬 처리된다.
- placeholder 부모 정리, 마지막 child 삭제 같은 후처리가 같은 스레드 안에서는 덜 꼬인다.
- FanPost Redisson 버전과 ArtistPost Stream worker 버전에 같은 설명 축을 적용할 수 있다.

- trade-off
- "왜 post lock이 아니라 thread lock인가"를 별도로 설명하지 않으면 구현 의도가 잘 안 보인다.
- delete 경로에서는 reply도 먼저 root id를 계산해 같은 락 키를 맞춰야 한다.

## 16. ArtistPost만 `async Redis Stream` 경로를 타게 한 이유는 모든 쓰기를 같은 복잡도로 가져가고 싶지 않았기 때문이다

- 선택
- FanPost, FanLetter 좋아요는 동기 처리로 남겼다.
- ArtistPost like/comment만 Redis Stream 기반 비동기 write-path를 사용한다.

- 이유
- 모든 도메인에 동일한 무거운 구조를 적용하면 학습 비용과 운영 복잡도가 너무 커진다.
- ArtistPost가 가장 고트래픽 가능성이 큰 영역이라, 복잡한 설계를 여기에 집중했다.
- 과제 발표에서도 "왜 어떤 곳은 단순 동기 처리로 충분했고, 어떤 곳만 비동기화했는가"를 설명할 수 있다.

- 얻는 이득
- 복잡도는 필요한 곳에만 집중된다.
- ArtistPost를 동시성/고트래픽 대표 사례로 삼을 수 있다.

- trade-off
- 도메인별 쓰기 일관성 모델이 완전히 동일하지 않다.
- 유지보수자는 "왜 ArtistPost만 다르게 동작하는지"를 이해해야 한다.

## 17. ArtistPost 트래픽 테스트는 단순 락 실험보다 `write-path 정합성 검증`에 가깝게 설계했다

- 선택
- `no lock / Lettuce v1 / Redisson v2 / Stream v3` 비교 테스트를 두었다.
- 별도로 `ArtistPostTrafficConvergenceIntegrationTest`로 좋아요, 댓글, mixed read/write 수렴 테스트를 만든 상태다.

- 이유
- ArtistPost의 핵심 문제는 "락을 걸었는가"만이 아니라, 비동기 소비와 flush 이후 최종 상태가 수렴하는가에 있다.
- 그래서 단일 요청 수준의 상호배제만이 아니라, burst 이후 최종 count와 상태가 맞는지를 검증할 필요가 있었다.

- 얻는 이득
- 단순 분산 락 실습보다 실제 읽기 모델 수렴을 더 강하게 증명할 수 있다.
- `20,000`, `30,000`, mixed traffic 같은 실험 결과를 문서화할 수 있다.

- trade-off
- 이 테스트는 "실서버 capacity benchmark"가 아니라 "로컬 환경에서의 수렴 검증"이다.
- 락 구현 비교와 스트림 아키텍처 비교가 섞여 보일 수 있어서 문서 프레이밍이 중요하다.

### 17-1. ArtistPost 좋아요 `v3`는 `pending state`로 "DB 반영 전 최신 의도"를 따로 들고 간다

- 선택
- 요청 경로에서 `artistPostId + memberId` 기준 pending state를 Redis에 잠시 저장한다.
- 각 pending state에는 `version`을 함께 붙여, 오래된 consumer가 더 최신 유저 의도를 지워 버리지 못하게 했다.

- 이유
- `v3`는 요청 시점에 DB를 바로 바꾸지 않고 command만 stream에 넣는다.
- 그래서 같은 유저가 아주 빠르게 두 번 토글하면, DB 현재값만 보고는 "지금 이 유저가 실제로 원하는 최신 상태"를 알기 어렵다.
- pending state를 두면 consumer 반영 전에도 요청 경로가 가상 최신 상태를 참고해 다음 토글을 해석할 수 있다.

- 얻는 이득
- 연속 토글에서도 유저가 방금 누른 최신 의도를 더 안정적으로 유지할 수 있다.
- consumer가 오래된 명령을 처리해도 `version`이 다르면 최신 pending state를 지우지 못한다.
- 요청 경로와 비동기 반영 경로의 역할이 분리되면서도 체감 상태는 덜 흔들린다.

- trade-off
- Redis에 보조 상태와 version 관리가 추가된다.
- enqueue 실패 시 pending state를 즉시 정리하지 않으면 "실제 DB와 요청 경로가 보는 상태"가 어긋날 수 있다.

### 17-2. V3 consumer의 DB 반영은 `조회 후 save/delete`보다 `INSERT IGNORE / 조건부 DELETE` 멱등 DML로 바꿨다

- 선택
- `desired=true`는 `INSERT IGNORE`로 반영한다.
- `desired=false`는 조건부 `DELETE`로 반영한다.
- 실제 row 수가 바뀐 경우에만 like delta 이벤트를 발행한다.

- 이유
- burst 상황에서 `select -> insert/delete` 경로는 round trip이 많고, 재시도 시 unique 충돌 비용도 커진다.
- 같은 명령이 다시 들어와도 "이미 있으면 no-op, 없으면 0건 삭제"로 끝나는 쪽이 consumer 처리량과 멱등성 모두에 유리했다.
- count delta까지 중복 발행되면 read model이 흔들리므로, DB에서 실제 변화가 있었을 때만 후속 delta를 내보내게 했다.

- 얻는 이득
- 재시도나 중복 소비가 있어도 예외 없는 no-op 처리로 수습하기 쉽다.
- consumer가 DB 상태 판정을 한 번의 조건부 DML로 줄일 수 있어 고트래픽에서 덜 비싸다.
- like count delta도 실제 변경 건에만 맞춰 발행돼 최종 수렴 설명이 단순해진다.

- trade-off
- JPA 기본 save/delete 흐름보다 구현 설명이 더 어렵다.
- DB 벤더의 DML 동작과 반환 row count 의미를 이해해야 한다.

### 17-3. Stream consumer는 `pending 재처리 + DLQ`로 독성 메시지가 전체를 막지 않게 했다

- 선택
- 매 poll마다 pending entries를 먼저 재처리하되, 그 결과와 무관하게 new message도 계속 읽는다.
- 재시도 횟수가 임계치를 넘으면 DLQ로 격리하고 본 stream에서는 제거한다.
- 성공 처리 후에는 ACK만 하지 않고 원본 엔트리도 삭제한다.

- 이유
- pending 하나만 남아 있어도 새 메시지를 아예 안 읽는 구조면 poison message 하나가 전체 스트림을 굶길 수 있다.
- ACK만 하고 원본 엔트리를 stream에 남겨 두면 단일 consumer group 구조에서는 메모리 누적이 계속될 수 있다.
- 나중에 수동 복구가 가능하려면 실패 payload와 최소 실패 메타데이터를 따로 남겨 둘 필요가 있었다.

- 얻는 이득
- 실패 메시지가 있어도 뒤의 정상 메시지가 계속 처리된다.
- DLQ를 통해 운영자가 실패 원인과 원본 command를 나중에 추적할 수 있다.
- 단일 consumer 전제에서 stream 길이 무한 증가를 어느 정도 통제할 수 있다.

- trade-off
- retry state, DLQ, pending read라는 보조 개념이 늘어난다.
- scale-out 시에는 consumer group 분산, pending claim 전략 같은 후속 설계가 더 필요하다.

### 17-4. like count는 `AFTER_COMMIT delta -> 3초 flush -> 일 1회 reconcile` 리듬으로 수렴시켰다

- 선택
- Reaction insert/delete가 실제 커밋된 뒤에만 `AFTER_COMMIT` 이벤트로 delta를 Redis에 쌓는다.
- scheduler가 기본 `3초` 주기로 delta를 DB `like_count`에 반영한다.
- 별도로 하루 1회 full reconcile로 전체 활성 ArtistPost count를 원본 기준 재정산한다.

- 이유
- 트랜잭션이 롤백됐는데 count delta만 먼저 반영되면 원본과 집계가 어긋난다.
- flush는 "최근 변경분만 빠르게 따라가는 경로", reconcile은 "혹시 남은 드리프트를 최종 정산하는 경로"로 역할을 나눌 필요가 있었다.
- 읽기 hot cache TTL도 `3초`라서 flush 주기와 맞추면 eventual consistency 리듬을 설명하기 쉽다.

- 얻는 이득
- 원본 Reaction 커밋과 count 집계 경계가 선명해진다.
- 요청 경로에서 count row hotspot을 피하면서도 화면 숫자는 짧은 주기로 따라가게 할 수 있다.
- flush 누락이나 운영 중 예외가 있어도 reconcile이 최종 안전망이 된다.

- trade-off
- scheduler, delta buffer, reconcile까지 운영 컴포넌트가 늘어난다.
- "즉시 강한 일관성" 대신 "짧은 지연 후 수렴" 모델을 받아들여야 한다.

### 17-5. count delta와 cache invalidation은 서비스 직접 호출보다 `TransactionalEventListener`로 분리했다

- 선택
- write 서비스나 stream processor는 "원본 row 변경"까지만 책임지고, 후처리는 도메인 이벤트 발행으로 넘긴다.
- 실제 후처리는 `@TransactionalEventListener(phase = AFTER_COMMIT)`에서 수행한다.
- 여기에는 `ArtistPostLikeDeltaEvent`, `ArtistPostCommentDeltaEvent`, `CommentCacheInvalidationEvent`, `FanLetterSpecialLikeCacheInvalidationEvent`가 포함된다.

- 이유
- 같은 트랜잭션 안에서 DB write와 Redis/cache 후처리를 직접 섞어 두면 서비스 메서드가 너무 많은 책임을 가진다.
- 더 중요한 이유는 롤백 안전성이다. 원본 row 저장이 실패했는데 cache invalidation이나 delta 누적만 먼저 실행되면 읽기 모델이 불필요하게 흔들릴 수 있다.
- 또 sync write 경로와 async stream write 경로가 "커밋 이후 후처리"라는 공통 계약을 공유하면, 후속 count/캐시 정책을 한 군데에 모아 설명하기 쉬워진다.

- 얻는 이득
- 원본 write 로직과 후처리 로직의 경계가 선명해진다.
- 댓글 캐시 무효화, FanLetter special-like cache clear, ArtistPost like/comment count delta 적재를 모두 같은 `AFTER_COMMIT` 규칙으로 맞출 수 있다.
- 나중에 후처리 정책이 바뀌어도 서비스 본문보다 listener 쪽만 수정하면 되는 경우가 많다.

- trade-off
- 메서드 본문만 읽으면 실제 부수효과가 바로 보이지 않아 흐름 추적 비용이 생긴다.
- 현재는 in-process 이벤트라서 "같은 애플리케이션 인스턴스 안의 커밋 후처리"에는 적합하지만, 분산 이벤트 버스 같은 보장은 별도 설계가 필요하다.

## 18. 대시보드는 일부러 `논캐시 오케스트레이션`으로 남긴 곳이 있다

### 18-1. Artist 홈 대시보드는 응답 정책을 먼저 고정하기 위해 캐시를 보류했다

- 선택
- 아티스트 홈 대시보드는 `latestArtistPost 1건 + hotFanPosts 6건 + hotFanLetters 4건`을 조립한다.
- 현재는 별도 캐시를 붙이지 않았다.

- 이유
- 이 API는 단일 테이블 조회가 아니라 여러 도메인 결과를 섞어 만든다.
- 어떤 조각을 얼마나 캐시할지보다, 먼저 어떤 응답 shape와 정책이 맞는지 정하는 쪽이 우선이라고 봤다.
- 또 홈 대시보드는 포스트 상세/피드처럼 같은 사용자가 짧은 시간에 여러 번 새로고침하는 화면이 아니라고 봤다.
- 즉 한 사용자가 같은 화면을 반복 조회해 캐시 hit를 크게 만들어내는 성격이 약하다고 판단했고,
  그래서 읽기 캐시를 붙였을 때 체감 이득도 상대적으로 작다고 봤다.

- 얻는 이득
- 조립 정책을 고정하기 전 premature cache 설계를 피할 수 있다.
- 이미 있는 `latest`, `HOT` 조회 로직을 재사용해 빠르게 완성할 수 있다.

- trade-off
- 호출이 많아지면 다음 최적화 포인트가 될 수 있다.
- 현재는 "정책 우선" 단계이지 "최대 성능 최적화 완료" 단계는 아니다.

### 18-2. 메인 홈도 "하나의 큰 피드"가 아니라 섹션 오케스트레이션으로 설계했다

- 선택
- 메인 홈은 `popularKeywords`, `subscribedArtistsLatestPosts`, `followedArtistMembersLatestPosts` 세 섹션을 조립한다.

- 이유
- 메인 홈은 서비스 탐색 허브에 가깝지, 하나의 타임라인이 아니다.
- 구독 섹션은 `artist별 최신 n건`, follow 섹션은 `writer 기준 전역 최신`으로 요구사항이 아예 다르다.

- 얻는 이득
- 섹션별 정책을 분리해 확장하기 쉽다.
- "구독은 artist 중심", "follow는 writer 중심"이라는 차이를 코드 구조에서 바로 드러낼 수 있다.

- trade-off
- repository 1회 조회로 끝나는 단순 API보다 조립 로직이 복잡하다.
- 캐싱을 붙이려면 섹션별 정책을 따로 고민해야 한다.

## 19. 구독 섹션과 follow 섹션의 조회 축을 다르게 잡은 것은 제품 의미 차이 때문이다

- 선택
- 구독 섹션은 `artistId -> 최신 N개 글` 맵 구조를 만든다.
- follow 섹션은 `writerIds -> 전역 최신 글`을 가져온다.
- follow 카드 응답은 `ArtistMember 메타데이터(stageName/profile) + 실제 post 응답`을 함께 묶는다.
- 카드의 실제 글 작성자 표시는 `stageName`보다 `post.writerNickname`을 우선한다.

- 이유
- 구독은 "내가 보는 아티스트별 최신 묶음"이 핵심이다.
- follow는 "내가 관심 있는 멤버들이 최근에 무엇을 썼는가"가 핵심이다.
- 둘을 같은 쿼리로 풀면 한쪽 요구가 깨진다.

- 얻는 이득
- 섹션 의미에 맞는 데이터 shape를 유지할 수 있다.
- `findLatestRowsByArtistIds`와 `findLatestRowsByWriterIds`의 용도가 분명해진다.
- follow 대상 메타데이터와 실제 post writer 표기를 섞지 않고 역할을 분리할 수 있다.

- trade-off
- 조회 메서드 수와 설명 포인트가 늘어난다.
- 특히 `artist별 top-N`은 단순 `limit`로 해결되지 않아 쿼리가 더 복잡해진다.
- 현재는 "한 Member가 동시에 여러 ArtistMember로 존재하지 않는다"는 가정 위에서 `writerId -> ArtistMember` 단일 매핑으로 조립한다.
- 미래에 한 멤버가 다중 소속을 허용하게 되면 follow 섹션 매핑 정책을 다시 설계해야 한다.

## 20. `artist별 최신 N개`를 가져오기 위해 서브쿼리를 사용했다

- 선택
- `findLatestRowsByArtistIds`는 아티스트별 최신 글 N개를 가져오기 위해 서브쿼리를 사용한다.

- 이유
- 여기서 필요한 것은 "전체 최신 글 몇 개"가 아니라, "아티스트마다 최신 글 몇 개씩"이다.
- 단순히 최신순 정렬 후 `limit`만 걸면 특정 아티스트 글만 몰려서 다른 아티스트 글이 빠질 수 있다.
- 그래서 아티스트별로 최신 글 N개를 맞춰 가져오기 위해 서브쿼리 방식을 사용했다.

- 얻는 이득
- 여러 아티스트를 한 번에 조회하면서도, 각 아티스트마다 필요한 개수만 맞춰 가져올 수 있다.
- 메인 홈 구독 섹션처럼 "아티스트별 최신 글 묶음"을 만들기 쉬워진다.

- trade-off
- 단순 정렬 + limit 쿼리보다 이해하기 어렵다.
- 데이터 규모가 더 커지면 이후 다른 방식으로 다시 최적화할 여지는 있다.

## 21. Follow는 "SNS 전면 기능"이 아니라 `Member -> ArtistMember` 최소 모델만 남겼다

- 선택
- Follow 방향은 `Member -> ArtistMember`로 고정했다.
- 토글과 홈 피드 조립에 필요한 조회만 둔다.
- soft delete 대신 hard delete 토글을 쓴다.
- 동시 follow 경쟁은 DB unique 제약으로 최종 정합성을 잡는다.

- 이유
- 처음에는 `Member -> Member` 형태의 더 일반적인 팔로우 모델도 생각할 수 있었다.
- 하지만 이미 과제 프로젝트 치고는 기능 수와 도메인 관계가 충분히 많았고, 여기서 팔로우까지 일반 SNS처럼 넓히면 복잡도가 더 커진다고 판단했다.
- 이번 과제에서 Follow는 완전한 SNS 모델이 아니라, "내가 가장 관심 있는 아티스트 멤버의 글만 따로 모아보는 공간"을 만들기 위한 최소 기능에 더 가깝다.
- soft delete를 쓰면 재팔로우 시 unique 처리와 상태 관리가 더 복잡해진다.
- 조회 후 insert 경쟁은 애플리케이션 코드만으로 완전히 없애기 어렵다.

- 얻는 이득
- 모델이 작고 설명이 명확하다.
- 홈 대시보드 조립에 필요한 데이터만 빠르게 뽑아 쓸 수 있다.
- 팔로우의 가장 실용적인 장점인 "관심 있는 아티스트 멤버 글만 따로 보기"에 바로 집중할 수 있다.
- 동시성 예외를 사용자 관점의 최종 상태로 해석해 500으로 올리지 않을 수 있다.

- trade-off
- 팔로워 수 집계, 추천, soft restore 같은 SNS 확장성은 낮다.
- unique 제약과 예외 재해석에 대한 이해가 필요하다.

## 22. FanLetter는 "댓글 없는 이미지 중심 콘텐츠"로 분리해 다른 게시물과 일부러 성격을 갈랐다

- 선택
- FanLetter는 팬 멤버십을 구독한 사람만 작성할 수 있게 했다.
- FanLetter는 댓글이 없다.
- 이미지 1장 정책을 쓴다.
- `special-like`는 persisted field가 아니라 Reaction 원본을 읽어서 조립한다.
- 아티스트 좋아요 표시는 "누가 눌렀는지"보다 "아티스트가 반응했다"는 대표 정보만 보여준다.

- 이유
- FanLetter를 아무나 쓰는 공개 글로 두면 FanPost와 역할 차이가 약해진다.
- 그래서 FanLetter는 "구독한 팬만 쓸 수 있는 전용 소통 공간"이라는 성격을 분명히 두고 싶었다.
- FanLetter를 댓글까지 있는 일반 커뮤니티 글로 만들면 FanPost와 구분이 약해진다.
- "아티스트에게 보내는 감정 표현형 콘텐츠"로 성격을 분리하려고 했다.
- special-like는 별도 필드로 중복 저장하기보다 읽기 시점 조립으로 유지했다.

- 얻는 이득
- 구독 기능의 효용을 FanLetter에서 분명하게 보여줄 수 있다.
- FanPost와 FanLetter의 역할 구분이 선명해진다.
- 이미지 1장 정책 덕분에 목록/상세 조립이 단순하다.
- "아티스트가 반응함"이라는 UX를 비교적 간단히 만들 수 있다.

- trade-off
- 작성 권한 장벽이 생긴다.
- 댓글 기반 상호작용은 포기한다.
- special-like는 읽기 시점 조립이라 추가 조회가 필요하다.

## 23. ArtistPost와 FanPost 목록 미디어는 `preview 6개`만 내려 UI 정책과 응답 크기를 맞췄다

- 선택
- 목록에서는 미디어 전체 대신 앞 `6개` preview만 내려준다.
- 전체 개수는 `mediaCount`로 표현한다.
- 상세에서는 전체 미디어를 붙인다.

- 이유
- 목록 카드에서 모든 미디어를 다 보내면 응답이 무거워진다.
- 실제 UI도 대표 몇 장만 보여주고 나머지는 개수로 안내하는 편이 자연스럽다.

- 얻는 이득
- 목록 응답 크기를 줄일 수 있다.
- base cache의 크기도 통제하기 쉽다.

- trade-off
- 목록만으로는 전체 미디어를 모두 볼 수 없다.
- preview 개수 `6`은 UI 정책이 바뀌면 함께 조정해야 한다.

## 24. YouTube 탭은 파일 업로드가 아니라 `외부 링크 아카이브`로 분리했다

- 선택
- YouTube 기능은 `URL -> videoId 추출 -> 외부 메타데이터 조회 -> 카드 메타 저장` 흐름으로 설계했다.
- 등록 권한은 해당 artist 소속 멤버만 가진다.
- writer stageName/profileImageUrl은 snapshot으로 저장한다.
- 스킴이 빠진 유튜브 링크도 `https://`를 붙여 한 번 더 해석한다.
- 목록은 `publishedAt` 복합 정렬보다 `id DESC` cursor를 먼저 썼다.

- 이유
- 기존 `MediaService`는 파일 업로드 중심이라 유튜브 링크 아카이브와 성격이 다르다.
- 아티스트 멤버 프로필이 바뀌어도 과거 카드가 흔들리지 않게 snapshot 저장이 필요했다.
- 사용자는 `youtube.com/...`, `youtu.be/...`처럼 스킴 없이 붙여 넣는 경우가 많아서, 이런 입력까지 완전히 invalid로 거절하면 UX가 거칠어진다.
- 목록 요구는 "최신 등록순" 정도로 충분해서 구현이 단순한 `id DESC`를 먼저 택했다.

- 얻는 이득
- 외부 링크형 미디어를 파일 업로드 도메인과 분리할 수 있다.
- 과거 카드의 표시 일관성을 유지할 수 있다.
- 설명하기 쉬운 cursor list 구조를 얻는다.

- trade-off
- 실제 유튜브 업로드 시간과 서비스 등록 시간은 다를 수 있다.
- 더 정교한 정렬 요구가 생기면 `publishedAt` 중심으로 바꿀 수 있다.

## 25. YouTube 중복 등록은 "선조회 + 즉시 flush + 재확인"으로 도메인 예외를 보장했다

- 선택
- 먼저 `existsByArtistIdAndYoutubeVideoId`로 선조회한다.
- 저장은 `saveAndFlush`로 즉시 무결성 오류를 감지한다.
- `DataIntegrityViolationException`이 나면 문자열 파싱 대신 실제 중복 존재 여부를 다시 조회하고, 진짜 중복일 때만 도메인 예외로 바꾼다.

- 이유
- 선조회만으로는 동시 요청 경쟁을 막지 못한다.
- 결국 최종 정합성은 DB unique 제약이 지켜준다.
- 예외 메시지 문자열은 DB 벤더나 환경마다 달라 믿기 어렵다.

- 얻는 이득
- 중복 경쟁에서도 사용자에게 일관된 도메인 에러를 줄 수 있다.
- DB 메시지 문자열에 로직을 의존하지 않는다.

- trade-off
- 예외 처리 코드가 단순 CRUD보다 길어진다.
- unique 제약과 flush 타이밍을 이해해야 한다.

## 26. 인덱스도 "쿼리 모양"에 맞춰 설계했다

여기서는 세부 DDL보다 설계 의도만 먼저 정리한다. 자세한 전후 비교는 `member-artistcontent-index-analysis.md`가 담당한다.

- 선택
- 일반 목록은 `artist_id + id DESC` 축에 맞춘 cursor 조회를 쓴다.
- 댓글 root는 `targetType + targetId + parent null + id DESC` 패턴을 전제로 둔다.
- reply는 `parent_id` 중심 조회를 둔다.
- follow는 `followerMemberId + id DESC` 축으로 읽는다.

- 이유
- 페이지네이션 전략을 먼저 정하고, 그 전략에 맞는 인덱스가 붙는 구조가 더 일관적이다.
- 단순히 "컬럼에 인덱스를 많이 붙이는 것"보다 실제 정렬/where 조건 순서가 중요했다.

- 얻는 이득
- cursor 기반 조회가 풀스캔보다 안정적으로 동작한다.
- `EXPLAIN`에서 왜 그 인덱스를 타는지 설명이 가능하다.

- trade-off
- 검색 `LIKE '%keyword%'` 같은 쿼리는 일반 B-Tree 인덱스 최적화 효과가 제한적이다.
- 그래서 검색은 캐시 최적화 포인트로, 게시글/댓글/팔로우 조회는 인덱스 최적화 포인트로 분리해서 설명하는 편이 낫다.

## 27. 요약: 이 파트의 공통 설계 원칙

이 파트 전체를 관통하는 의사결정은 대체로 아래 네 줄로 요약할 수 있다.

- 자주 안 바뀌는 읽기 구조와, 자주 바뀌는 숫자 상태를 분리했다.
- 최신순 피드에서는 `offset`보다 `cursor`를 우선했고, HOT처럼 정렬 축이 달라지는 곳은 그 축에 맞는 커서를 따로 설계했다.
- 모든 곳에 가장 무거운 구조를 쓰지 않고, 복잡도는 ArtistPost 같은 핵심 트래픽 구간에 집중했다.
- 강한 실시간 일관성이 꼭 필요하지 않은 곳은 짧은 stale과 TTL을 받아들이고, 대신 캐시 효율과 구조 단순성을 얻었다.
